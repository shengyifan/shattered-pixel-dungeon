## 实玩与恢复

- 每层先规划路线、资源获取、角色与装备升级、敌人处理和工具使用；发生关键变化后重新规划。
- 从同一授权 `spdctl` 连接获取公开状态。读取源码以解释机制，不读个人存档或私有 audit，
  不从历史地图、截图、摘要、角色默认值或“正在思考”状态推断当前游戏事实。
- 保持一个实际写入者。准备新楼层、陌生机制或路线分歧时再调用只读顾问；避免递归重复委派。
- 同步成功回复本身是当前观察。`in_progress` 后通过 `settle` 确定原 `rid`，保留原动作结果，
  不用成功 `state` 查询冒充原动作成功；不能对未知、已完成或进行中的动作盲重放。
- `move/cell` 可能导致攻击、开门、拾取、换层或提示窗。操作完成不保证已到指定格，检查实际回复。
- 游戏暂停意味着立即停下输入并保留连接；不擅自保存、退出、重启或清理。
  恢复时按协议处理可能尚未收齐的请求，再从新的公开观察作决定。
- 胜负必须以原生公开结局为证据；击败首领、获得护符和选择结局是不同节点。

## 解码与故障判断

- Java控制器的外层协议成功与Python语义校验成功是两项检查。
  解码失败保留完整原始字节、失败帧身份、原动作ID/结果及保存回执，不删除难解字段或猜测默认值。
- 显示血条前景向上取整、背景四舍五入会产生至多一格溢出。样本21/4/22仍按原值保留；
  当前约束是正整数total和 `0 <= filled <= with_shield <= total + 1`，basis为displayed。
  这不是精确HP，也不是对其他字段放宽验证的理由。
- `STALE_STATE` 表示该绑定已经失效，单靠错误码不能判断是操作疏忽还是导出时序问题。
  确认原动作REJECTED后，若用户允许恢复，再取新观察、重新判断并使用新绑定。
  CLI.8.0.1已修复红格/护盾纯视觉淡出造成的多余revision；真实战斗变化仍使旧绑定失效。
- 软settle预算耗尽的pending不等于硬响应超时。`response_pending`表示内部查询还没收齐；
  继续settle同一请求，不重发，不把state/cancel当作隐式恢复。
- 原生stderr中的LWJGL/JDK诊断不等于游戏回复或动作失败；根据完整NDJSON和原始传输确认边界。

## 维护与证据

- 用户若限定只修Python并保留游戏，就保持这个范围。包内Java修复需要后续启动才生效，不能声称热更新。
- 使用隔离profile回归，不用真实游戏扩展覆盖率。源码枚举、测试夹具、包验证和完整实玩是不同证据。
- CLI、协议、schema、游戏版本分别管理。运行时修复后同步相关版本面并核验实际输出；
  纯文档/技能迁入不需要假装发布一个新的CLI版本。
- 验证实际包的ARM64、版本、帮助、构建清单与签名。绘制相关比较用同一个冻结帧；
  同rev的两次实时帧可能因允许的视觉变化而不同。
- 验证后做范围明确的本地GPG签名提交，并检查暂存区、签名与工作区。推送、tag和发布遵循用户单独授权。
