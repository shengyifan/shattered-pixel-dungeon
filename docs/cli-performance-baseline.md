# CLI.0.2 性能基线

> 文档整理说明：配套的历史验收 JSON 已按用户要求删除；原始运行数据也已清空。本页保留当时的验证说明，旧结构化结果可从 Git 历史查阅，不能作为 CLI.0.9.0 的新验收结果。

本报告测量 CLI.0.2.0 的完整采集和审计成本。生产代码没有加入计时字段，公开观察、`state_version` 和数据库持久化要求均保持原样。测试工具只存在于 `desktop-control/src/test`，不会进入应用包。

所有游戏与菜单输入都通过公开 NDJSON 完成。测试使用 `desktop-control/build/fixtures` 下的新目录，没有读取个人存档。密集场景由测试启动器构造，合成审计历史重复同一个完整检查点；二者都不是通关证据，也不代表一个真实长局的数据增长。

## 环境与方法

- 生产基线：`60a08116056412803f90b48119240a39113c2cab`，CLI.0.2.0；各进程使用复制后固定的测试运行时。
- 本机：Apple M5，10 个逻辑处理器，16 GiB 内存，macOS 26.6.2，ARM64 Temurin 25.0.4；Xerial SQLite JDBC 3.53.4.0。
- 现场读取实际 writer 配置：public/internal 均为 `journal_mode=delete`、`synchronous=3`（EXTRA），`fullfsync=1`。没有切换到 WAL，也没有关闭同步来换取速度。
- 三个场景：主菜单、普通 Warrior 开局、人工密集场景。密集场景保留原生 Actor/Sprite/采集路径，放入 40 个敌人、8 个真实 `DriedRose.GhostHero` 和 4 类气体。
- 每个场景先预热 5 次 `state.get`，然后分别测量 30 次 `state.get`、30 次 `history.list`、30 次 `request.get`。两个游戏场景另测 10 次实际 `inventory.open`，每次通过 `ui.back` 关闭；这些物品窗口操作不消耗游戏回合。
- 完整采集、公开投影、文件采集、编码、压缩、恢复各预热 5 次再采样 25 次。p50/p95 使用排序后的最近秩，保留原始毫秒数组；10 次操作的 p95 等于本轮最大值。
- 真实管道耗时从 Python 编码/写请求开始，到读取并解析对应完整 NDJSON 响应结束，包含排队、审计事务与管道 I/O。它不是单个 Java 方法的执行时间。

采集探针在 render thread 和真正的 Actor handoff monitor 内调用原 `GameSnapshotter.capture()`，包括公开投影、对象图、静态根、RNG、声明范围内的游戏文件和构建清单；这项方法计时不包含 `UiBridge` 与协议编码。编码/数据库基准使用最后一个真实 CLI 观察的完整 `GameController.State`，包括公开 UI 和内部 interaction 字段，没有删减模型或文件。探针额外的编码与文件输出在释放 Actor monitor 后执行，不持有 monitor 等待 SQLite。游戏场景验证了重复只读探针没有改变 RNG、HP 或位置。

离线 SQLite 基准用测试专用 `Connection` 代理包装原 writer 的 `commit()`，代理原样转发所有调用。`complete` 计时包含生产 `encodePair`、SQL 写入与双库提交；`JDBC commit` 只包真正的提交调用，不含之前的 SQL。恢复分别测量内存中的压缩块、逐块读取数据库和公开 `request.get` 的完整恢复路径。

## 结果

完整毫秒数组、环境、计数和本机证据索引见 cli-performance-baseline.json（历史 JSON 已删除，可查 Git 历史）。三场景来自同一个生产构建 ID；其各自 30 次连续 `state.get` 都保持同一个公开状态版本。

实际 NDJSON 请求耗时，单位毫秒，数值为 **p50 / p95**：

| 请求 | 主菜单 | 普通开局 | 密集场景 |
| --- | ---: | ---: | ---: |
| `state.get` | 120.90 / 158.05 | 206.49 / 222.12 | 202.38 / 240.87 |
| `history.list`，最多 100 条 | 127.90 / 156.89 | 187.65 / 222.06 | 217.87 / 256.12 |
| `request.get`，完整公开响应与快照 | 126.02 / 153.97 | 184.53 / 191.02 | 207.75 / 236.23 |
| `inventory.open`，含操作前后快照 | — | 327.05 / 345.02 | 400.49 / 454.85 |

主菜单、普通开局、密集场景在采集探针前分别完成了 101、137、137 个真实公开请求，包含菜单导航和预热。普通开局本轮有 14 个 Actor、8 个 mob、1 类 blob；密集场景有 56 个 Actor、48 个 mob（其中 8 个同伴）、4 类 blob。密集场景单次查询中位数略低于普通开局只是本轮数据，不能据此推断实体增加会降低成本。

各方法的计时，单位毫秒，数值为 **p50 / p95**：

| 方法 | 主菜单 | 普通开局 | 密集场景 |
| --- | ---: | ---: | ---: |
| 完整 `GameSnapshotter.capture` | 2.04 / 10.58 | 6.04 / 8.35 | 7.39 / 9.68 |
| 单独公开游戏投影 | 0.0005 / 0.0005 | 0.034 / 0.043 | 0.112 / 0.128 |
| 单独声明范围文件采集 | 0.058 / 0.065 | 0.085 / 0.092 | 0.099 / 0.111 |
| 内部完整 JSON 编码 | 2.45 / 2.90 | 3.97 / 4.30 | 5.11 / 5.75 |
| 已编码整份 JSON 的 gzip 参考值 | 9.75 / 13.80 | 14.01 / 14.38 | 16.55 / 17.32 |
| 生产 `encodePair`：拷贝、分块、编码、gzip、hash | 27.03 / 30.78 | 51.75 / 53.29 | 62.74 / 64.83 |
| 单次真正的 paired JDBC commit | 23.67 / 41.25 | 22.77 / 24.60 | 23.78 / 43.61 |
| `complete`：编码、写入、提交 | 58.90 / 74.23 | 85.75 / 88.80 | 97.89 / 119.30 |

gzip 参考值处理的是两份已经编码好的整份 JSON，生产 `encodePair` 还处理分块与内容身份，两者不能直接互换。这些不同阶段、不同 JVM 的分位数也不能相加还原管道耗时。

1000 条密集场景合成历史的直接读取成本，单位毫秒：

| 直接读取 | p50 | p95 |
| --- | ---: | ---: |
| 历史前 100 条 | 0.73 | 0.87 |
| 历史最后 100 条 | 0.67 | 0.80 |
| 历史完整 1000 条 | 7.48 | 8.23 |
| 公开 `getRequest`，含前后快照恢复 | 0.42 | 0.51 |
| 内部完整快照：内存压缩块恢复 | 25.19 | 29.65 |
| 内部完整快照：数据库逐块读取并恢复 | 33.90 | 37.04 |

直接读取没有记录一次新的 CLI 请求；真正执行 `history.list` 或 `request.get` 时，这次查询本身仍有完整审计与快照，所以端到端耗时明显更高。

## 历史与存储的含义

主菜单和普通开局各构造 100 条完整 `state.get` 审计，密集场景构造 1000 条。每条都有不同请求 ID、原始请求、完整公开响应、对应完整快照及输出标记，走原 `AuditStore.begin/complete/markOutputAttempt`。这是同一检查点反复查询时的复用情形，不能用其空间增长率推算整局不同楼层、物品变化和更多存档文件产生的空间。

每轮都将所有公开字段和内部字段完整解压恢复，再比较规范 JSON，验证字段没有丢失。快照 occurrence ID 仍逐次独立分配；相同内容的压缩块在原数据库内容表复用。历史列表只读取分页索引，不嵌套过去的响应和快照，详细内容由 `request.get` 获取。

| 存储指标 | 主菜单，100 条 | 普通开局，100 条 | 密集场景，1000 条 |
| --- | ---: | ---: | ---: |
| 单份完整公开快照 JSON，bytes | 2,016 | 17,182 | 41,433 |
| 单份完整内部快照 JSON，bytes | 1,147,900 | 2,241,562 | 2,617,589 |
| 内部唯一压缩块总量，bytes | 360,011 | 637,861 | 745,036 |
| 独立快照 occurrence 数 | 100 | 100 | 1000 |
| 内部实际唯一 blob 数 | 653 | 1607 | 1932 |
| public 数据库，MiB | 0.88 | 3.57 | 80.84 |
| internal 数据库，MiB | 1.35 | 4.48 | 81.91 |

1000 条密集检查点只有约 745 KB 的内部压缩块，两个库合计仍达到约 163 MiB。主要原因是完整公开响应保存在 `requests` 和 `exchanges` 中，两个库各保留一份；41 KB 的观察在这里会重复。当前分块复用解决了快照正文的重复，没有解决响应正文的重复。

## 对后续优化的判断

当前更明显的成本在生产配对编码与持久化提交，完整采集本身较小。后续可以优先评估完整响应正文的无损压缩或内容引用复用，以及对构建清单、字段清单和内容未变的快照块复用已经编码压缩的结果；必须保留原始内容的完整还原，并为可变对象使用正确的内容身份和有界缓存。这样可以直接针对已经测得的 CPU 与空间成本。

本轮没有降低 SQLite 同步级别、合并必要的执行前记录、跳过查询审计或删减隐藏内部数据。是否更改事务边界涉及已确定的崩溃和重复保护语义，应单独评审，不能只按速度决定。

## 复跑

从仓库根目录执行：

```sh
./gradlew :desktop-control:writeTestRuntimeClasspath --console=plain
python3 desktop-control/src/test/python/performance_smoke.py --scenario menu --history 100 --requests 30
python3 desktop-control/src/test/python/performance_smoke.py --scenario simple --history 100 --requests 30
python3 desktop-control/src/test/python/performance_smoke.py --scenario dense --history 1000 --requests 30
```

脚本为每轮创建新的隔离目录，固定运行时副本；输出 `performance-result.json`、完整采集探针结果、快照和本轮合成双库。这里的计时是本工作站的一次开发期基线，未控制其它后台程序、温度和操作系统文件缓存，不能视为所有机器的延迟保证。目前没有完整长局性能样本。
