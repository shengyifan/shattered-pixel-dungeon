## 观察到的问题

最后一次近战击杀返回 `ok=true`、`status=completed`、`phase=player_ready` 和版本 `:58`。约 10 秒后，下一条游戏动作原样使用该版本，点击地图中已知的锁门 `cell=661`，返回 `STALE_STATE`。

两条动作之间，本控制客户端没有发送任何其他游戏动作。错误后的只读查询返回 `:59`。对完整公开观察做结构比较，**只有 UI 发生变化**：

- `ui-68`（`Attack Enemy` / `tag_attack`）从 `enabled=true` 变成 `false`。
- 对应的 `ui.activate` 动作从广告列表移除。
- 两条标记为 `floating_text` 的数值文本 `7` 和 `1` 消失。
- 英雄、背包、地图、可见实体和视觉线索完全一致。

因此，本记录聚焦于“击杀完成后返回的可操作状态随后因 UI 延迟变化而失效”。不是锁门交互本身已经执行后失败。公开 `request.get` 将失败动作记录为 `REJECTED`，其 before/after 快照一致；英雄仍在 `cell=634`，锁门仍为 `Locked door`。

## 静态源码线索与判断边界

以下均来自当前仓库源码。实测已经确认公开状态差异，下面的因果链仍需在独立实例中复现验证，没有读取本局内部状态来确认私有字段。

1. `core/src/main/java/com/shatteredpixel/shatteredpixeldungeon/ui/AttackIndicator.java:90-100`：背景隐藏后先 `enable(false)`，但保留 `active` 直到 `delay` 降到 0；可见时将 delay 重置为 `0.75f`。私有 `enabled` 与组件 `active` 不是同一个字段。
2. 同文件 `:125-142`：没有可攻击候选后将 `lastTarget` 置空并隐藏背景、停用点击语义；`:181-185` 的实际点击另检查私有 `enabled`。
3. `game-control/src/main/java/com/shatteredpixel/shatteredpixeldungeon/control/game/UiBridge.java:476`、`:500-502`：公开 `enabled` 和是否广告 `ui.activate` 使用 `gizmo.isActive()`。这与上述延迟停用的时序对应。
4. 同文件 `:126-141`：意图签名已经排除浮动战斗文本和游戏日志文本，但保留 enabled 等其他控件属性。因此单纯把本次归因于伤害/经验飘字消失没有源码支持；攻击按钮状态变化是更直接的线索。
5. `game-control/src/main/java/com/shatteredpixel/shatteredpixeldungeon/control/game/GameController.java:295-305`、`:472-494`、`:513-519`：稳定判定等待已声明的回调、Actor 和后续绘制；目前不能仅据此保证攻击指示器的延迟停用已经完成。
6. 同文件 `:547-556`：UI 意图签名参与 `state_version` 计算。`desktop-control/src/main/java/com/shatteredpixel/shatteredpixeldungeon/control/desktop/MachineSession.java:142-145`、`:195`：动作前重新观察，版本不匹配会在派发前拒绝。

后续修复建议先针对“最后一个可攻击目标被近战击杀”建立真实引擎回归，核验立即返回和跨过原有 0.75 秒延迟后的按钮可用性与状态版本。再覆盖仍有其他可攻击目标、正常外部输入使旧版本失效的情况。应核对原生点击语义和公开广告的一致性，不应简单屏蔽所有 enabled 变化或自动重试来掩盖问题。
