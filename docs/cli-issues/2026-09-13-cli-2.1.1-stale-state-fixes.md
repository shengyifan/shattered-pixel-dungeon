## 本次根因与改动

`AttackIndicator.checkEnemies()` 在没有候选目标时隐藏背景、停用私有点击语义。`update()` 保持组件 active 直到原有 delay 耗尽；这个设计让界面继续完成更新。`UiBridge` 通过 `gizmo.isActive()` 描述公开 enabled 和可执行动作；enabled 又参与意图签名。

因此旧版击杀响应可能仍广告 `Attack Enemy`；原生更新停用组件后，该按钮从动作列表消失，下一条请求的版本就被拒绝。公开实战证据中只有 UI 变化，英雄、地图、背包和实体均不变。浮动伤害/经验文字本来就被意图签名排除，不能把本次问题简单归结为飘字消失。

生产行为改动仅在 `AttackIndicator.java` 增加 7 行：当 `exists && active && !bg.visible` 时报告尚有待完成交互。保留原 update、0.75 秒延迟、点击回调和游戏规则。既有控制器等待这段自然更新及后续绘制；当前仍有攻击目标时不阻塞。零延迟但尚未执行最后一次 update 的初始指示器也被覆盖；停用或移除的节点不会挂住稳定检查。

## 是否应重试

可以设计客户端有界恢复，但恢复应建立在“原动作确定未执行”和“重新观察后仍适合执行”上。

1. 收到明确 `STALE_STATE` 时，该动作在游戏回调前被拒绝。用新 ID 获取 `state.get`；如果响应丢失或结局不明确，先查原 `request.get`。
2. 核对新 scope、phase、目标、提示、资源和广告动作，重新取得 control/locator。控件标签相同不能证明仍对应同一对象或同一操作。
3. 在新状态上重新作出决策。如果原意图仍然成立，才以新 ID、新版本提交；设置较小的尝试上限，持续失效时记录并停止。

服务端没有足够信息替调用方判断意图是否仍然合适，因此不能仅把提交版本换成最新值再执行。`move.step` 可能在新状态下从移动变成攻击或拾取，背包 locator 也可能已经对应另一件物品。

`completed`、`in_progress`、`EXECUTION_UNKNOWN`、`EXECUTION_UNCERTAIN` 不能按陈旧拒绝重试：查询原结果或等待结算；不确定时保持隔离。若当前任务规定“遇错暂停”，恢复策略必须服从该要求。本次修复测试没有引入自动重放，手册补充了上述边界。
