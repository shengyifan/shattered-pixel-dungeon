# CLI.6.0.1: controller startup on shared terminal descriptors

2026-09-20. This patch fixes default `spdctl control --machine` startup on a terminal/PTY. CLI advances from 6.0.0 to 6.0.1; protocol 6, audit schema 9, the independent CLI v6 profile directory, transport format 1 and base game 3.3.8 are unchanged. The [CLI.6.0.0 implementation](../cli6-implementation.md) and [clean rebuild](../cli-rebuild-6.0.0-20260920.md) remain historical records.

## Incident and evidence boundary

The original default controller launch failed while emitting its initial handshake. The child's public raw trace contains a complete, parseable 6,704-byte successful handshake including its newline. The externally delivered controller output was partial; only afterward did the trace report input EOF and exit. This localizes the failure after child protocol delivery, during the controller's output to its caller. The original startup diagnostic was generic and did not retain an errno; errno 35 (`Resource temporarily unavailable`) was observed in a separate isolated reproduction, not recovered from the original log.

Redirecting controller stdout and stderr into different files avoided the shared terminal condition and allowed startup. That was a workaround, not a protocol or game fix. It is no longer required by CLI.6.0.1. A caller parsing NDJSON must still keep stdout and stderr separate: deliberately merging both streams onto one terminal permits diagnostic text and JSON to interleave.

The previously opened game had already exited before this implementation batch. The remaining idle controller connection was closed; no running game was restarted in place. Implementation and regression evidence use isolated synthetic processes or fresh test profiles, not personal saves or private audit data.

## Root cause and change

In `StableController.launch`, CLI.6.0.0 started its `run --machine` child with inherited stderr. The native relay in `spdctl-bootstrap.c` sets its stdin, stdout and stderr to `O_NONBLOCK` for its own streaming loop. With a shared terminal, inherited stderr and the controller's stdout can refer to the same open-file description. File status flags belong to that description: changing the child's stderr also changes the parent's stdout. Java `PrintStream` then encounters backpressure on an unexpectedly nonblocking descriptor and can emit only part of a JSON line before reporting failure.

The controller now supplies three fresh child pipes, including explicit `ProcessBuilder.Redirect.PIPE` for stderr. A dedicated daemon forwards raw diagnostic bytes to controller stderr; it never passes them to the NDJSON reader or decodes/re-encodes them. The protocol reader and writer remain independent. Diagnostic display is best-effort: after a failed sink the forwarder continues draining the child, and final waiting after child exit is limited to five seconds. A blocked diagnostic consumer cannot hold the independent protocol stream's Java lock. This does not promise lossless terminal display when the consumer is broken or permanently stalled; the native child remains the sole owner of original transport recording.

The launcher now distinguishes child-start, controller-output and controller-input failures as `CONTROLLER_CHILD_START_FAILED`, `CONTROLLER_OUTPUT_FAILED` and `CONTROLLER_INPUT_FAILED`, with `CONTROLLER_FAILED` as the fallback. It prints only the stage and exception class, never arbitrary exception messages, stack traces or paths. `CONTROLLER_DIAGNOSTIC_READ_FAILED` identifies a diagnostic-pipe read failure. These stderr diagnostics are not protocol replies or proof of an action's outcome. The controller does not create profile logs for them.

No native relay nonblocking logic, raw transport bytes, game rules, request replay policy, current-revision binding, profile migration or viewer styling changes are included.

## Regression evidence

The new `test_controller_pty.py` compiles the production Java controller and native relay and supplies a disposable GUI-free engine. It does not launch the real game, open Terminal.app or access a personal profile. The engine fragments multibyte UTF-8 output and the caller intentionally applies output backpressure.

The old inherited-stderr implementation failed a 128 KiB synthetic handshake: the externally received first line was only 1,164 bytes and invalid JSON, terminal `F_GETFL` changed from 65,538 to 65,542 (`O_NONBLOCK` added), and the controller reported output I/O failure. This reproduces the same descriptor-sharing mechanism independently of the original incident's smaller handshake.

All five new integration tests passed against the fix:

- Shared terminal startup with a handshake larger than the original 6,704-byte response; delayed input remains open and later state/quit requests complete.
- A response exceeding 64 KiB, a slow terminal consumer and split UTF-8 characters; output remains complete and terminal flags do not change.
- Input EOF with a large final diagnostic tail; diagnostics drain without an extra protocol request.
- Broken controller stdout; failure is reported and the handshake is never replayed.
- Stalled stderr with independent stdout; state replies continue without being blocked by the diagnostic writer.

The tests also compare original child SEND/RECV bytes and stderr independently, verify one trace owner, fresh short IDs and ordinary child exit. These synthetic results establish descriptor, framing and shutdown behavior; they are not gameplay or real-window visual coverage.
