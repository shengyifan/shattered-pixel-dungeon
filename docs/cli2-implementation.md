# CLI.2.0.0 多语言来源改造

> 后续清理说明：2026-09-13 本次 CLI.3.0.0 清理重建已按用户要求删除旧 build 产物及三份本地实战故障 JSON。以下保留 CLI.2.0.0 当时的实施与验证记录；旧输出路径及当时保留的附件不表示文件目前仍存在。

本批实现用户批准的最小侵入方案：保留原游戏 String 接口，以中央观测钩子、弱身份来源注册表和必要局部组合操作输出官方英文及安全资源 key。

## 固定边界

- CLI.2.0.0、协议 2、审计 schema 5；不兼容旧协议/旧审计，不删除或迁移旧 profile。
- GUI 采用游戏原语言和显示分支；CLI 从已冻结、玩家可知的来源渲染英文。
- 不按字符串内容反查，不使用生产字节码转换、agent 或隐藏字符。
- 用户/外部原文明确标记后保留；未鉴定身份、未绘制或裁切内容不得通过 key/参数泄漏。
- 纯文案呈现失败局部降级；真实执行、稳定边界和审计不确定性继续保留保护。
- 验证仅使用新建隔离 profile；原生游戏规则和存档格式不变。

## 来源与最小原版改动

原版的资源、名字、说明等 API 继续返回 `String`。成功资源查找把最终命中的 key、GUI 模板和已物化参数交给中性 `RuntimeObserver`；原版不认识协议 DTO、注册表或 SQLite。来源树、弱身份索引、英文模板冻结和纯输出投影都在 `game-control/control/game/text`。

普通赋值和传参不改。Java AST 类型检查定位了 1,076 处实际显示字符串拼接，使用返回 String 的 helper 保留来源，原数字运算、资源 key、路径和存储键保留。`checkTextSources` 是 `game-control:test` 的依赖，扫描 1,192 个 core 文件；196 个保留操作对应 162 条精确表达式及次数说明，没有文件级豁免。769 处代码更新目录构造调用另有输入信任边界检查。名单见 `game-control/src/test/resources/text-composition-exclusions.json`。

基础文本控件绑定来源，在相同文字重新赋值时也更新身份；销毁与浮字复用释放绑定。语言设置继续走原版 `seamlessResetScene`、控件销毁和 `GameLog.wipe`，不增加另一套游戏生命周期。已冻结的历史来源不随注册表释放而失效。

范围之外的变化没有借本次迁移加入：游戏规则、伤害公式、随机种子生成与原生存档格式保持原样。种子只在三个实际显示入口调用新的 `DungeonSeed.displayCode`，原 `convertToCode` 编码方法保持原样。资源文件仅修正了瑞典语符文之刃两条说明中重复的百分号转义。

## 公开数据与审计

- 文本字段旁边的 `text_sources` 提供最终资源 key、组合树、显示数字来源，或明确的 user / external 标记；没有原类查找链或当前游戏对象。
- 冻结令牌只保存已经通过玩家知识和显示范围筛选的数据。裁切、透明、无字体或未绘制内容不能通过完整 key、英文模板及参数复原。
- 数字舍入、字符串截断和布尔/哈希格式只保存实际显示片段；不公开原始精度、被截断尾文或原哈希输入。普通完整整数和字符串仍保留便于机器使用的 scalar / resource 来源。
- 原文字面值的 substring / replace 只保留已物化结果及 origin；被删尾文、搜索参数和原字符下标不会藏在来源树内。结构前缀仅接受可证明的固定标点来源；源资源的数字/内容删除保守降级。英文格式化先检查宽度和精度预算。
- GUI 没有显示、英文却需要的参数不能公开。已完整显示的资源允许保留无参数、无模板的安全 key 引用；其余不支持的来源整体隐藏。
- `presentation.status` 与动作 `status` 独立。文本故障不重放动作，也不丢弃日志和保存回执；真实回调、稳定边界、关键快照或审计失败仍进入原不确定性保护。
- schema 5 保存 canonical 玩家快照、实际发送响应、呈现状态、GUI 语言及不可变的 session 构建/版本字段。历史响应按记录返回，不重新翻译；历史查询不要求当前游戏观察成功。
- 所有请求都必须显式携带整数 `protocol_version: 2`。旧 schema 在获取会写文件的锁及创建 profile 内容前只读拒绝，不自动迁移或删除。

## 验证期间发现并修正的问题

1. 官方 key 可以带 `!` 和 `?`，例如 `actors.mobs.goo.!!!`，不能用过窄的标识符正则拒绝。
2. 无参数资源文案不经过 Formatter；匈牙利语 `50%-kal` 不能被测试错误识别为格式说明符。显式 `Messages.format` 的零参数 `%%` 则必须按原 Java 行为处理。
3. 禁用的灰色按钮仍由 `Group.draw` 绘制，不能用 `active` / `alive` 判定文字是否显示；字体、有效透明度、几何裁切和真实浮字绘制证据分别检查。
4. `StyledButton` 的缓存全文不能绕过子文字的可见片段；裁切 BitmapText 的隐藏尾文也不能改变公开意图版本。扫描菜单时把 RTB 当作文字叶节点，避免观察时填充字词 camera 缓存。
5. 菜单也需要后续完整绘制确认。`Game.render` 先 draw 后 step，新 HeroSelectScene 曾在首 draw 之前返回；标题随后出现使旧版本失效。控制器现在等待当前菜单的下一帧，保持原 GUI 和版本保护。
6. 恢复备注测试中的来源缺口实际位于此前的存档预览种子编码，尚未进入恢复后的备注窗口。显示编码已补来源，备注业务未被改写。
7. 显示器休眠时 GLFW 可返回零主显示器句柄；英语与韩语均能复现同一启动异常。保持显示器唤醒后，同一构建的韩语完整流程通过。这不是语言代码或字体问题。启动异常现先写审计并释放等待请求，返回实际引擎错误，避免关闭流程将它延迟成 30 秒状态超时。

资源语料检查的已验证批次覆盖 4,830 个官方英文 key × 23 种注册语言，共 111,090 项；其中 111,087 项完整英文，3 项是明确的 key 引用可见性降级，格式/投影缺陷为 0。三项为繁中长鞭的两条能力说明和波兰语矮人国王的激怒对白：原 GUI 省略参数，双世界检查保证改变这些未显示值不会改变公开令牌或输出。

基础真实 GUI 矩阵曾在构建 `95267e8915de048f8fac32828d501e6c9a45366ba64ac6728c824aacf5c637f7` 下完成 23/23：原菜单选择战士、新局、物品说明、返回、保存以及正常退出。后文另记最终构建的完整复测，不把这批较早结果改写为后续构建实测。


深场景测试的控件选择也保留可见性边界。俄语备注窗口的 Edit Title 可能在原 GUI 中裁切；测试只在完整公开备注上下文、两个已知邻接动作和唯一剩余可点击控件同时成立时，通过当前 control 选择，并检查原始编辑器后置状态，不恢复被隐藏的标题 key，不修改原 UI 字号或布局。
